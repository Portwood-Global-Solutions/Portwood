# Download one merged PDF from a Portwood bulk job

A nonprofit can select its year-end receipt template and donor Accounts, run Bulk Document Generation, wait until the job shows **Ready to download**, then download a single PDF with its receipts in the selected order. The individual statements stay private in Salesforce. The browser writes the merged PDF to the user's device. Salesforce remains responsible for template generation and record access.

The [benchmark and runbook](README.md) demonstrate this workflow with a fictional annual contribution statement and 100,000 synthetic Accounts, including 200,000 Opportunities and 400,000 line items. The benchmark used the existing HTML renderer, which calls `Blob.toPdf()` for each statement. It ran in eight scratch orgs and replayed the exported Files through localhost for Chrome. Implement and verify the authenticated Lightning download before exposing the action to customers.

## Build the job output

1. Add an opt-in PDF output mode to [`docGenBulkRunner`](../../force-app/main/default/lwc/docGenBulkRunner) that creates individual private Files and offers one merged download from Job History. Continue using the existing template selection, filter, sort, and progress surfaces.
2. Have [`DocGenBulkController.submitJobInternal`](../../force-app/main/default/classes/DocGenBulkController.cls) validate the job, record the input count, and persist a stable input order before asynchronous rendering. Apply the selected sort and break ties by source record ID. Assign each record its ordinal once. Salesforce can execute batch scopes out of sequence. [Salesforce Batch Apex documentation](https://trailhead.salesforce.com/content/learn/modules/asynchronous_apex/async_apex_batch)
3. In [`DocGenBatch`](../../force-app/main/default/classes/DocGenBatch.cls), query related data by scope and call `DocGenService.generatePdfBlobFromData` where the template and prefetch path support it. Keep each scope bounded by expected document size and complexity. Write individual PDFs and their output entries with bounded DML. Record each successful file's exact `ContentVersion.Id`, source record ID, ordinal, byte count, and checksum. Persist failures with their ordinals. Use the job and ordinal as the idempotency key so scope retries can fill gaps without emitting duplicate statements.
4. Make the manifest immutable once the successful job is ready to download. A full download becomes available only when every planned ordinal has a successful file. Report failed inputs and provide a way to rerun them. Keep existing bulk output modes and their release limits independent of this mode. The current `analyzeJob` product threshold and `getJobGeneratedPdfs` lookup need explicit review. The latter re-queries records with a 2,000-record limit and reconstructs order from file titles, so it cannot serve as the large-job manifest.

## Serve and merge the private files

1. Show **Download merged PDF** on the completed job and in Recent Jobs. Reuse the existing `DocGen_Job_Complete` notification to open the authenticated job when its manifest has been committed. Authorize every paginated manifest request against both the job's download policy and the exact Files. Apply sharing and CRUD/FLS in subscriber orgs. The job's internal sharing model gives broader record visibility, so enforce an explicit download entitlement in addition to read access. Use authenticated Salesforce File links or endpoints and keep PDF bytes out of Apex response bodies. Require Salesforce authentication at each download entry point.
2. Port the [streaming PDF writer](scripts/lib/portwood-browser-pdf-merge.mjs) and [browser worker](scripts/bench/portwood-pdf-merge-browser.worker.mjs) into the Lightning surface. Use the existing bundled [pdf-lib static resource](../../force-app/main/default/staticresources/pdflib) at its known version. Verify Worker creation, CSP, Lightning Web Security, the chosen authenticated File endpoint, and storage APIs inside an installed package in scratch. Keep localhost replay as a benchmark fixture.
3. Fetch ahead with a bounded request queue. Verify each response's exact length and manifest checksum, append its pages in ordinal order, then free its input buffer. The proof writes incrementally to the Origin Private File System (OPFS) and finalizes the PDF cross-reference table at the end. Tie saved checkpoints to the frozen manifest and job identity, and validate the last durable file offset before resuming. Include progress and actionable errors for a revoked File, exhausted browser storage, or an unsupported browser. Browser capabilities and interrupted-user-session behavior require separate tests on the intended Salesforce surface.
4. Track the Files created for a job and define who can retain or remove them. Where generated Files are also intentionally linked to source records, treat those attachments independently from temporary download artifacts. Measure remaining org File storage and set chunk sizes based on the customer's document mix and retention policy.

## Reuse the authenticated downloader

The [downloader reference](download-reference/) already connects a real Lightning ready notification to an authenticated download page. In the 256 MiB trial, that page used six concurrent private reads, ordered disk writes, and a final checksum that matched the archive reference. In the resume trial, a Salesforce Standard User closed the original tab after 5,690,700 bytes. Chrome reused 18 of 36 chunks and fetched only the remaining 5,690,699 bytes. The final SHA-256 matched and all 36 observed range reads reported zero Apex callouts.

Use the same completion handoff, progress, parallel reads, owner and revision checks, and recovery behavior for bulk output. Keep the two inputs explicit. A completed byte stream can supply verified ranges to the download sink. A job containing independent PDFs supplies ordered File versions to the PDF writer, which copies page objects and creates a new cross-reference table. The browser persists the merge's committed ordinal and writer state against the immutable manifest. After a refresh, verify the manifest and local checkpoint, continue at the next ordinal, and reject changed, missing, or unauthorized Files.

For the first release, serve standard Salesforce Files to the authorized recipient. The scratch archive objects demonstrate a separate way to stage a large byte stream. Use them as a reference for range validation and resume, and require a separate product decision before adding archive storage to the managed package.

## Acceptance checks

- At the small end, compare every page with the individual PDFs from a real installed Portwood job. Include repeated sort values, one multipage statement, and exact version checks after a new version is uploaded to a source file.
- Run 10,000 Accounts end to end in an org with measured headroom. Repeat the 100,000 benchmark with synthetic data and report browser version, org count, scope sizing, storage, generation time, download time, merge time, and verification time. The earlier 100,000 test establishes the document shape and processing pipeline. For a single-org 100,000 target, qualify File storage and throughput in that org.
- Verify one output entry per selected Account and ordered pages per entry. Prove no gaps, duplicates, unexpected callouts, or public distributions. Confirm that a different user cannot query the manifest or download Files they cannot access, including after a user's access changes mid-download.
- Interrupt a batch transaction, a File download, and a browser merge separately. Verify recovery writes only missing statements, reports unrecoverable failures, resumes at the last intact browser checkpoint, and produces the same output hash for the same ordered immutable sources.
- Use the reference fixture to verify every donor, gift, amount, date, and line item. Also test long templates, large PDFs, and shared or multiply linked Salesforce Files for the product path. Keep existing PDF modes and current small-job behavior covered.
