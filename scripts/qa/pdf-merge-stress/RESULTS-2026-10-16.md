# PDF merge stress results - October 16, 2026

Completed **123 unique scenarios** in a dedicated Winter '27 scratch org:
**92 successful merges, 11 size/count guard rejections, and 20 intentional governor
limit failures**. All 92 successful outputs passed independent PDF validation.
The action's configured limits were left unchanged.

## What a Flow can use today

| Limit / verified case                   | Synchronous           | Queueable             |
| --------------------------------------- | --------------------- | --------------------- |
| Maximum source versions per packet      | 100                   | 100                   |
| Combined source bytes per action call   | 393,216 (384 KiB)     | 786,432 (768 KiB)     |
| 100 distinct one-page text PDFs         | Passed; 1,337 ms CPU  | Passed; 1,351 ms CPU  |
| Exact byte-limit packet, two image PDFs | Passed; 714 ms CPU    | Passed; 1,348 ms CPU  |
| One byte above the combined input limit | Rejected before merge | Rejected before merge |
| 101 input versions                      | Rejected before merge | Rejected before merge |
| Runtime CPU / heap limit                | 10,000 ms / 10 MB     | 60,000 ms / 25 MB     |
| Runtime SOQL limit                      | 100                   | 200                   |

The 100 distinct text PDFs totaled 149,686 bytes and produced an 86,704-byte PDF.
Both IDs supplied in one Text value and Text collections were already functionally
verified before this capacity run; this matrix uses the collection input.

Byte limits count every repeated occurrence and are shared across multiple Flow
interviews in the same action invocation. Available heap can lower the allowed
input budget. These are input budgets, not output-file size limits or guarantees
for every PDF under that size.

The action runs in its caller's transaction. **Calling it from a Screen Flow does
not enqueue a Queueable.** Async results here came from an explicit Queueable
wrapper in the test harness.

## How far the underlying engine got

These tests bypassed the action's count and byte guards. They are experimental
successes, not supported limits for the Flow action.

| Workload / largest observed success              | Synchronous                                           | Queueable                                    |
| ------------------------------------------------ | ----------------------------------------------------- | -------------------------------------------- |
| Combined image-PDF input bytes                   | 4,982,970 (~4.75 MiB); 7,843 ms CPU                   | 8,391,884 (~8.00 MiB); 12,957 ms CPU         |
| Largest individual source in a successful packet | 2,622,598 (~2.50 MiB), plus a small text PDF          | 6,293,734 (~6.00 MiB), plus a small text PDF |
| Small one-page PDF entries                       | 1,000; 13,069 ms CPU, already above the nominal limit | 4,000; 58,610 ms CPU                         |
| Next count tested after that success             | 1,250: CPU limit failure                              | 5,000: CPU limit failure                     |

Count probes above 100 **cycled 100 distinct ContentVersions**. They did not create
4,000 distinct uploaded source files. The supported 100-version action case used
100 distinct source versions.

Do not plan synchronous capacity around the 1,000-entry success: the measured CPU
exceeded the transaction's reported 10-second limit. Even 750 entries reported
10,076 ms. A 400-entry engine case took 5,382 ms. CPU headroom is necessary for
the surrounding Flow and other work in the same transaction.

Heap failures were **not monotonic in file size**. Two image PDFs totaling about
4.50 MiB failed in sync even though another 4.75 MiB packet passed. An async
6.00 MiB packet failed even though an 8.00 MiB packet passed. Async 10, 12, and
16 MiB image packets failed heap checks; 80 smaller image-PDF entries totaling
10,517,120 bytes also failed. File layout and allocation behavior matter; there
is no universal safe megabyte ceiling established by these largest successes.

## Small files can still exhaust CPU

Two compressed PDFs, each 47,766 bytes with 5,000 blank pages, totaled only
**95,532 bytes (~93.3 KiB)**. The action accepted the input size, but synchronous
execution hit an uncatchable Apex CPU limit while assembling the output. The
same 10,000-page packet passed in Queueable using 16,871 ms CPU and produced a
1,268,390-byte PDF.

Two 3,000-page compressed blank PDFs passed sync at 9,891 ms, already too close
to the CPU ceiling for a general Flow recommendation. This proves that total
bytes alone cannot protect arbitrary uploaded PDFs from governor failures.
Use the Flow action's fault connector for platform-limit failures; a governor
exception cannot be converted into the normal `success = false` response.

## Validation and measurement scope

Fixtures covered text PDFs, incompressible grayscale image streams, long
documents, compressed object/xref streams, ordinary AcroForms, duplex padding,
and highly compressed page-heavy documents. Successful outputs were downloaded
and checked with pypdf and pikepdf/qpdf for page count, page order, text, decoded
image hashes, unchanged encoded image-stream hashes, and zero syntax warnings.
The two 25-form packets also retained all 25 namespaced canonical fields, their
values, widgets, and appearance streams. Representative large image and form
outputs were rendered with Poppler and visually inspected.

Sync tests called the production invocable through a scratch-only Apex REST
harness. Async tests called it inside a real Queueable; a Finalizer saved
uncatchable governor failures separately. The engine probes used the existing
`mergePdfCvs` API directly. Source and output Files were synthetic test data.
No external PDF-processing service was used.

CPU includes merging and inserting the output File, but excludes the Queueable
result-log insert and offline verification. `heapBefore` and `heapAfter` are
current heap readings, not peak heap. Failed transactions have no after-the-fact
CPU or heap measurements. Scheduling latency is not merge CPU time. This was a
scratch org with little surrounding automation, not a loaded customer org.

The runtime-reported 10/25 MB heap limits match Salesforce's
[Winter '27 release announcement](https://developer.salesforce.com/blogs/2026/10/developers-guide-to-the-winter-27-release).
The merger classes were compiled at API 66; the org ran API 68.

The evidence supports keeping the current conservative action caps. Raising them
should follow additional resource checks and tests against representative user
documents, rather than adopting a largest observed engine success as a limit.
